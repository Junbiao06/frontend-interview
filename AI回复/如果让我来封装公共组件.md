如果让我来封装公共组件，我不会一开始就把所有看起来相似的代码都抽出来，而是会先判断它到底是“真正可以跨业务复用的组件”，还是“只是当前业务里长得比较像的组件”。

我一般会从以下几个方面考虑。

第一，我会对组件进行分层。

最底层是基础 UI 组件，例如 Button、Input、Dialog、Select、Table、Skeleton。这些组件只负责最基础的样式和交互，不应该包含具体业务逻辑。

比如 Button 可以接收 variant、size、disabled、loading、className 和 onClick，但它不应该知道“点击后是创建文档还是删除用户”。

如果项目使用 shadcn/ui，我通常会直接基于 shadcn 的组件进行调整，而不会再无意义地封装一个 MyButton。只有当项目需要统一 loading 状态、权限控制或者埋点等行为时，我才会在它上面再做一层封装。

第二层是通用组合组件。

这类组件通常由多个基础 UI 组件组合而成，例如 ConfirmDialog、SearchInput、EmptyState、PageHeader、Pagination、FileUploader 等。

以 ConfirmDialog 为例，它可以接收标题、描述、确认按钮文字、取消按钮文字和 onConfirm 回调。组件内部只负责弹窗展示和交互，至于确认以后是删除文档、退出组织还是取消订单，应该由调用方决定。

例如：

```tsx
<ConfirmDialog
  title="确定删除该文档吗？"
  description="删除后将无法恢复"
  confirmText="删除"
  onConfirm={handleDelete}
/>
```

这样 ConfirmDialog 就不依赖具体业务，可以在不同模块中复用。

第三层是业务组件。

例如 DocumentCard、DocumentMenu、EditorToolbar、OrganizationMemberList。这些组件已经明确依赖某个业务的数据结构和操作，所以我不会强行把它们放到公共组件中，而是把它们放在对应的业务模块里。

我的目录通常会这样设计：

```text
components/
├── ui/
│   ├── button.tsx
│   ├── input.tsx
│   └── dialog.tsx
└── common/
    ├── confirm-dialog.tsx
    ├── empty-state.tsx
    └── search-input.tsx

features/
├── documents/
│   └── components/
│       ├── document-card.tsx
│       └── document-menu.tsx
├── editor/
│   └── components/
└── organizations/
    └── components/
```

这样做的好处是职责比较清晰：`ui` 存放基础组件，`common` 存放跨业务使用的组合组件，`features` 存放具体业务组件。

在设计组件的 Props 时，我会重点注意几个问题。

首先是保持单一职责。

一个组件最好只解决一个明确的问题。例如 SearchInput 只负责搜索框的展示和输入，不应该同时负责请求接口、处理分页、展示搜索结果。

请求数据和业务状态可以放在父组件或者自定义 Hook 中：

```tsx
const { keyword, setKeyword, results } = useDocumentSearch();

return (
  <SearchInput
    value={keyword}
    onChange={setKeyword}
    placeholder="搜索文档"
  />
);
```

这样 UI 和业务逻辑就分开了，组件也更容易复用和测试。

其次，我会优先使用组合，而不是设计大量布尔类型的 Props。

例如下面这种设计就容易失控：

```tsx
<Card
  isDocument
  isTemplate
  showAuthor
  showDelete
  showShare
  isCompact
/>
```

随着需求增加，这个组件内部会出现大量条件判断，不同 Props 之间还可能发生冲突。

相比之下，我更倾向于通过 children 或插槽进行组合：

```tsx
<Card>
  <CardHeader>
    <DocumentIcon />
    <CardTitle>项目计划</CardTitle>
  </CardHeader>

  <CardContent>
    文档内容
  </CardContent>

  <CardActions>
    <ShareButton />
    <DeleteButton />
  </CardActions>
</Card>
```

这样使用者可以自由组合不同区域，公共组件本身也不需要知道具体业务。

然后，我会让组件尽量支持受控模式。

例如 SearchInput 的 value 和 onChange 由父组件传入，而不是把搜索状态完全保存在组件内部。这样父组件可以更加方便地同步 URL 查询参数、触发接口请求或者清空输入内容。

```tsx
interface SearchInputProps {
  value: string;
  onChange: (value: string) => void;
  placeholder?: string;
  disabled?: boolean;
}
```

事件 Props 的命名也要表达业务语义，例如 onConfirm、onCancel、onOpenChange，而不是使用 handleClick1、handleClick2 这种不明确的名字。

样式方面，我会保留一定的扩展能力，例如支持 className，但不会让调用方控制组件内部的所有细节。公共组件应该提供统一的默认样式，同时允许在特殊场景下进行少量覆盖。

如果使用 TypeScript，我会给组件定义清晰的 Props 类型，并尽可能复用原生元素的属性：

```tsx
interface ButtonProps
  extends React.ButtonHTMLAttributes<HTMLButtonElement> {
  variant?: "default" | "outline" | "ghost";
  size?: "sm" | "md" | "lg";
  loading?: boolean;
}
```

这样 Button 除了支持自定义属性，也可以继续使用 disabled、type、aria-label 等原生属性，组件的可访问性和扩展性都会更好。

对于复杂组件，我还会把展示逻辑和状态逻辑拆开。

例如一个文件上传组件可能包含文件选择、类型校验、上传进度和错误处理。如果把所有代码都写在一个组件里，后期会很难维护。我会把上传逻辑抽成 useFileUpload Hook，组件只负责展示：

```tsx
const {
  upload,
  progress,
  isUploading,
  error,
} = useFileUpload();
```

这样同一套上传逻辑既可以用在拖拽上传组件中，也可以用在普通上传按钮中。

至于什么时候应该封装，我通常不会以“出现一次重复代码”作为标准。因为两个地方现在看起来一样，不代表它们以后会一起变化。

我一般会在一个组件出现两到三次，并且确认它们的结构、行为和变化方向都比较一致之后，再提取为公共组件。

如果只是样式相同，但业务行为不同，我可能只提取样式或者基础结构，而不会强行合并成一个大组件。

另外，我封装完成后还会检查几个问题：

1. 组件是否只负责一件事情。
    
2. 是否包含了不应该出现的具体业务逻辑。
    
3. Props 是否清晰，是否存在大量布尔值。
    
4. 是否支持 className、ref 和必要的原生属性。
    
5. 是否方便测试和维护。
    
6. 如果将来新增一个使用场景，是否需要大量修改组件内部代码。
    

所以总结来说，我封装公共组件的思路是：先区分基础 UI、通用组合和业务组件；然后通过清晰的 Props、受控模式和组合式设计降低组件耦合；业务逻辑尽量放在父组件或自定义 Hook 中；最后根据真实的复用场景进行抽象，避免过度封装。

我认为一个好的公共组件，不是功能越多越好，而是职责清晰、接口稳定，并且使用者不需要了解它的内部实现就可以正确使用。
