下面聊一下你简历中的 RAG AI 助手：

当用户输入“公司的年假制度是什么”和“帮我查询张三的工资”时，系统如何判断分别走向量检索还是业务工具？

请重点说明：

- RAG 的完整流程，包括切分、向量化、检索和生成；
- 模型如何调用工资、考勤等业务工具；
- 如何防止员工通过自然语言提示词查询其他人的敏感数据；
- 为什么不能只在 Prompt 中告诉模型“不要越权”。

这部分我会采用“意图路由 + RAG 检索 + 受控业务工具”的方式处理。

用户请求进入后端后，先通过 JWT 获取 `userId`、角色和员工身份，再由 LangGraph Agent 判断问题类型：

- “公司的年假制度是什么”属于制度类问题，走 `search_policy` 向量检索工具；
- “帮我查询张三的工资”属于实时业务查询，走工资查询工具；
- “我今年还剩多少年假”则调用个人年假余额工具，而不是查询制度文档。

RAG 分为离线入库和在线问答两个阶段。

离线阶段，我会读取员工手册、年假制度、考勤制度等文档，按照标题、章节和段落切分成多个文本块，并保留文档名称、章节、适用角色、生效时间等元数据。每个文本块通过 OpenAI Embeddings 转成向量，存储到 MongoDB Atlas，并建立 Vector Search 索引。

在线查询时，系统先将用户问题向量化，在 MongoDB 中召回相似度最高的几个文本块，同时根据用户角色过滤可见内容。之后把召回内容、问题和回答约束传给模型，要求模型只能依据检索到的制度内容回答，并尽量返回制度名称和章节。如果相似度低于阈值，就告诉用户没有找到可靠依据，而不是让模型自由编造。

业务工具则采用 LangChain Tool 和 LangGraph 的 ToolNode。比如定义：

- `getMyPayslips`：查询当前员工工资单；
- `getEmployeePayslips`：管理员查询授权员工工资；
- `getMyAttendance`：查询当前员工考勤；
- `getLeaveBalance`：查询当前员工年假余额。

模型通过 `bindTools` 获取工具描述。当它生成工具调用后，LangGraph 将请求交给对应的 ToolNode，工具执行数据库查询，再把结果返回给模型生成自然语言回答。工具参数使用 Zod 校验，模型不能直接生成 MongoDB 查询语句。

以“查询张三工资”为例，普通员工调用工资工具时，工具不会信任模型传入的 `employeeId`，而是从 JWT 的 `userId` 出发，通过：

```
userId → employee.userId → employee._id → payslip.employeeId
```

查询当前员工自己的工资。如果普通员工试图在自然语言中指定张三，工具层仍然会拒绝。管理员才可以查询指定员工，但服务端还会校验张三是否属于管理员的部门或组织范围。姓名只用于服务端搜索和消歧，最终仍然要转换成员工 ID 并进行权限校验。

我不会只在 Prompt 中告诉模型“不要越权”，因为 Prompt 不是安全边界。模型可能受到提示词注入影响，也可能错误理解用户身份、错误解析员工姓名，或者被检索文档中的恶意内容干扰。

因此权限必须放在模型之外，由后端强制执行：

- API 层验证 JWT；
- Agent 根据身份暴露有限工具；
- 工具层再次执行 RBAC；
- 数据库查询必须带上用户归属条件；
- 返回结果前过滤敏感字段，并记录审计日志。

所以模型只负责理解问题和组织答案，向量库负责提供制度依据，业务工具负责访问真实数据，而最终的数据权限始终由后端和数据库查询条件控制。
