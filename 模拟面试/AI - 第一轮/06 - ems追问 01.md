继续追问 JWT 的安全边界：

你的 `protect` 中间件直接使用 JWT 中的 `role` 判断权限。假设某个管理员被降级为普通员工，但他之前签发的 JWT 还没有过期，那么他是否仍然可以调用管理员接口？

请说明你会如何处理：

- JWT 中是否应该保存 `role`；
- 角色变更后如何立即生效；
- Token 过期、刷新和撤销如何设计。

是的，按当前项目实现，如果管理员被降级为普通员工，而旧 JWT 还没有过期，他仍然可以调用管理员接口。

原因是当前 `protect` 只做了 JWT 签名和有效期校验，然后把 Token 中的 `role` 放到 `req.session`；`protectAdmin` 又直接判断：

```
req.session?.role === "ADMIN"
```

当前 JWT 有效期是 7 天，所以角色变更最多可能要等旧 Token 过期后才生效。

关于是否保存 `role`，我的看法是：可以保存，但不能把它作为唯一的权限来源。JWT 中的 `role` 可以用于前端展示或普通接口的快速判断，但对于工资、员工管理等敏感接口，后端应该根据 JWT 中的 `userId` 查询当前用户的最新角色和状态。也就是说，JWT 中可以保存角色快照，但服务端数据库中的角色才是最终依据。

角色变更时，我会在修改用户角色的同时，让后续请求立即失效旧权限。常见方案有两种：

第一，在 `protect` 中验证 JWT 后，根据 `userId` 查询数据库中的用户，获取最新 `role`、账号状态和权限，再由 `protectAdmin` 判断数据库角色。这样管理员降级后，下一次请求就会被拒绝。

第二，在用户表中维护 `tokenVersion` 或 `authVersion`。签发 Token 时把当前版本放进 JWT，角色变更、密码修改或强制退出时递增数据库版本。中间件比较 Token 版本和数据库版本，不一致就拒绝请求。这个方案仍然需要查询数据库，或者结合短时间缓存和权限变更时的缓存失效。

Token 生命周期方面，我不会让访问 Token 维持 7 天。更合理的设计是：

- Access Token 设置较短有效期，例如 10～15 分钟；
- Refresh Token 设置较长有效期，例如 7～30 天，并在数据库或 Redis 中保存哈希、用户、设备、过期时间和撤销状态；
- 刷新时采用 Refresh Token Rotation，每次刷新都签发新的 Refresh Token，旧 Token 立即失效；
- 退出登录、角色变更、密码修改时，撤销对应 Refresh Token，会话版本递增；
- 如果需要立即让已经签发的 Access Token 失效，可以通过 `authVersion` 校验、Redis 黑名单，或者统一轮换 JWT Secret。轮换 Secret 会让所有用户的 Token 同时失效，适合紧急情况。

当前项目实际上只有一个有效期 7 天的 JWT，没有独立 Refresh Token 和撤销机制，这属于可以继续改进的地方。对于前端存储，Access Token 更适合放在内存中，Refresh Token 使用 `HttpOnly`、`Secure`、`SameSite` Cookie，降低被 XSS 直接读取的风险。核心原则是：JWT 负责证明用户身份，数据库或权限服务负责决定用户当前是否仍然拥有这个角色。
